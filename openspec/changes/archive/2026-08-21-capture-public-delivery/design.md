## Context

See [proposal.md — Why](./proposal.md#why) for the motivation.

This design captures behaviour that is already shipped and running; it expects no code change. Public redirect resolution is attempted only after a `GET` or `HEAD` request has produced a not-found response, and it is never attempted for `/admin` or a path below `/admin/`. Resolution considers active redirect rows, matches the requested path against forms with and without leading and trailing slashes, and returns a permanent redirect only when the matched row has a non-empty destination. Otherwise, the original not-found response is preserved.

The public post list contains published posts only, orders them by publication date from newest to oldest, and returns twelve posts per page. A non-integer page becomes page 1, and the page is bounded from 1 through 1000. The list retrieves only the title, slug, excerpt, and publication date that it renders.

## Goals / Non-Goals

**Goals**

- Record the observable redirect-resolution and public post-list contracts that the running system already satisfies.
- Preserve the editor UI as a privilege boundary that public redirect data cannot shadow.
- State the cost and safety bounds of not-found resolution and public-list pagination.
- Give future changes an explicit contract against which to assess compatibility.

**Non-goals**

- Changing redirect, routing, post-list, storage, or editor behaviour.
- Redesigning redirect matching, adding loop or chain detection, or restricting destinations.
- Changing the post page size or adding another public post field.
- Specifying the editor screens used to manage redirects or posts.

## Decisions

### D1. Resolve redirects on the not-found path rather than ahead of routing

Redirect resolution remains conditional on an otherwise not-found `GET` or `HEAD` response.

**Rationale:** Successful routes are the common case and should not pay for a redirect lookup. Waiting until routing has failed keeps the database cost off normal page and asset delivery while still recovering moved public addresses. The consequence is deliberate but material: every 404 now incurs a database lookup, including misses generated by bots and hostile scanning traffic.

**Rejected alternatives:** Checking redirects before routing on every request was rejected because it would add database work to all traffic and would let redirect data compete with valid routes. Maintaining a separate ahead-of-routing redirect pass was also rejected because it duplicates routing precedence and spends the lookup before knowing whether recovery is needed.

### D2. Exclude the editor UI from redirect resolution

The `/admin` path and every path below `/admin/` remain outside redirect resolution.

**Rationale:** This is a privilege boundary, not merely a routing preference. Without the exclusion, an editor able to create a redirect row could shadow an administrative path and divert requests away from the protected editor UI.

**Rejected alternatives:** Relying on route ordering was rejected because a later routing refactor could silently reverse the precedence. Validating only the destination was rejected because a benign destination does not make it safe for editor-controlled data to capture a privileged source path. Reserving individual known admin pages was rejected because new administrative paths would be unprotected until separately listed.

### D3. Match tolerant path forms at read time rather than normalising at write time

Resolution compares a requested path with the stored source in forms that tolerate leading- and trailing-slash differences.

**Rationale:** Existing rows may already contain any of the accepted forms, including values created in another environment. Read-time tolerance preserves their meaning without a data rewrite and makes promoted redirects behave consistently after they move. The cost is a broader lookup that compares multiple candidates on every eligible 404 rather than one canonical value.

**Rejected alternatives:** Normalising the stored source when an editor saves it was rejected for this capture because it changes write behaviour, requires existing rows to be migrated or handled specially, and could make imported or promoted legacy rows behave differently. Matching only the literal stored value was rejected because it would turn harmless slash differences into unexplained misses.

### D4. Return a permanent rather than temporary redirect

A resolved redirect returns status 308 and preserves the request method semantics of a permanent redirect.

**Rationale:** Redirect rows represent durable address changes, so a permanent response tells browsers and intermediaries that the old address has been replaced and avoids repeated resolution after caching. Status 308 also avoids the method rewriting associated with some older redirect responses.

**Rejected alternatives:** A temporary redirect was rejected because it would understate the editor's intent and cause clients to keep consulting the old address. A method-changing permanent response was rejected because redirect resolution also accepts `HEAD` and should not imply that clients may change the request method. The trade-off is that browsers and intermediaries may retain a 308 after an editor changes or removes the row, so a mistaken redirect can outlive the current configuration.

### D5. Clamp the page parameter rather than reject it

The requested post-list page becomes an integer between 1 and 1000, with invalid input falling back to page 1.

**Rationale:** Pagination is a navigation input, and a safe page is more useful to a visitor than an error for malformed, negative, or absurd input. Clamping also places a hard ceiling on the work a hostile parameter can request.

**Rejected alternatives:** Returning an error for an invalid or out-of-range page was rejected because it turns a recoverable navigation mistake into a failed page. Passing the value through unchanged was rejected because a huge page could force the data service to calculate or traverse a correspondingly huge offset, increasing latency and resource use, while malformed values could surface avoidable query errors.

### D6. Use field-selected, page-bounded post queries

The public list retrieves one page of twelve published posts and selects only title, slug, excerpt, and publication date.

**Rationale:** The list should pay only for the records and fields it renders. A fixed-size page keeps query, transfer, and rendering cost stable as the number and richness of posts grow, while field selection avoids transferring private, large, or irrelevant post content.

**Rejected alternatives:** Fetching every published post and paginating in the application was rejected because memory, transfer, and render preparation would grow with the archive and eventually make the index slower for every visitor. Fetching complete post records was rejected because the body and other unused fields add cost and widen accidental data exposure without changing the list. Using an unbounded page size was rejected for the same growth behavior.

### D7. Capture the shipped contract rather than redesign it

This change records the running behaviour as the current contract, including choices that may merit separate revision.

**Rationale:** Undocumented behaviour is already depended upon and is easier to change accidentally than an explicit contract. Capturing it now creates a baseline for deliberate follow-up work without mixing reconciliation with product redesign. Timing matters because redirects are on the promoted list of `add-environment-promotion`; they are about to move between environments, so their post-promotion behaviour needs a stated verification target.

**Rejected alternatives:** Deferring documentation until every redirect risk is redesigned was rejected because promotion would proceed without a contract and because unrelated design questions would block reconciliation. Quietly improving matching, destination policy, caching, or pagination in this change was rejected because that would turn a no-behaviour-change capture into an unreviewed feature change. Omitting uncomfortable current behaviour was rejected because a partial contract would make verification misleading.

## Risks / Trade-offs

### R1. Not-found flooding creates database load

Every eligible 404 performs redirect resolution. Automated probing or a deliberate flood of random paths can therefore turn otherwise cheap misses into sustained database traffic, even though valid routes do not pay this cost.

### R2. Redirect loops and chains are not prevented

A row can point back to its own source or participate in a cycle, and several rows can form a chain. Clients may spend multiple round trips following a chain or eventually stop a loop with an error; this capture does not add graph validation or a hop limit.

### R3. A permanent response can outlive an editor's change

Browsers, shared caches, and other intermediaries may cache a 308. Changing or deleting the redirect row does not guarantee that those clients immediately stop using the old destination.

### R4. Tolerant matching can admit an unintended match

Treating leading- and trailing-slash forms as equivalent can make a row match a request the editor did not anticipate, particularly where another component treats those paths as distinct. The convenience is coupled to a broader matching surface.

### R5. A destination can be off-site or hostile

The captured resolver requires a non-empty destination but does not establish that it is same-site or trustworthy. An editor account with redirect access, or promoted redirect data from another environment, can therefore direct visitors to an external or hostile location.

### R6. Page bounds limit rather than eliminate expensive misses

Page 1000 is bounded but can still require substantially more offset work than page 1. The clamp prevents unbounded growth from the input; it does not promise constant database work for every accepted page.

## Migration Plan

There is no schema change, no data migration, and no expected code change. Verification is reconciliation against the running system:

1. Request an existing public route and a missing public path with `GET`, `HEAD`, and a non-read method. Confirm that valid routes are unchanged, only not-found `GET` and `HEAD` requests are eligible for resolution, and an unmatched request preserves its original not-found response.
2. Request `/admin` and a missing path below `/admin/`. Confirm that neither is resolved through public redirect data. Where exercising a matching row would require new data, use an existing non-production fixture or the existing acceptance harness rather than mutating the running data set.
3. Against an existing active redirect fixture, request each supported leading- and trailing-slash form and confirm that all resolve to the same non-empty destination. Against an inactive fixture, confirm that the original not-found response remains.
4. Inspect a matched response and confirm status 308 and the expected `location` header. Inspect an unmatched response and confirm its status, headers, and body remain the original not-found response.
5. Open the public post list with an invalid page, a page below 1, a normal page, and a page above 1000. Confirm invalid and low values behave as page 1, the normal page is retained, the high value is capped at 1000, and no page renders more than twelve posts.
6. Compare the visible list with the running post data. Confirm unpublished posts are absent and published posts are ordered by publication date from newest to oldest.
7. Observe the running list's data request through request tracing and confirm it asks for a bounded page and only title, slug, excerpt, and publication date. Confirm the rendered list contains no unselected post fields.

If implementation and a requirement disagree, resolve the disagreement as a defect or an explicitly reviewed contract change; do not weaken the requirement merely to make verification pass.

## Open Questions

None. The shipped choices needed for this reconciliation are known and testable; loop prevention, destination restrictions, cache-reversal strategy, and alternative matching are potential future changes rather than unknowns blocking this contract.
